# Changelog

All notable changes to MCP Tools for Elementor are documented in this file.

## Unreleased

- New (**security**): **the transport guard no longer depends on SiteAgent being installed.** 1.30.0 shipped two guards, and neither covered a fork-only site on its own. The registration shield (`meta.mcp.type = 'private'`) works only for as long as a co-installed server keeps honouring that convention — Angie 1.1.12 compares the raw value, but the bundled adapter's own helper coerces anything outside `tool|resource|prompt` back to `tool`, so if Angie ever adopts it the shield silently reopens. The execution guard closes that, but it lives inside `Governance::run_governed()`, and `wrap_ability()` returns every ability untouched when SiteAgent's snapshot engine is absent. On a site running this fork **without** SiteAgent — a configuration this plugin is meant to support — the entire protection therefore rested on another plugin's continued good behaviour. A write-capable ability's `permission_callback` is now wrapped with a transport check that runs on **every** site: a caller that cannot present gateway context is refused before the ability is reached, with a 403 rather than a fatal.
  - **Presence, not verification.** The grant is checked for existence here and verified once, later, by the governance layer. Verifying it twice would burn its single-use nonce and reject the second check — the legitimate call would fail on its own approval.
  - Without SiteAgent's verifier there is nothing that *could* validate a grant, so a foreign write is refused outright rather than waved through on an unverifiable header.
  - The gate **wraps** rather than replaces: the ability's own capability check still runs, and runs last, so this can only ever deny more than before.
  - Read-only abilities are not gated at all — an assistant on another server answering "what is on this page" from this plugin's data is the point of the read-only bridge.
  - One definition of "writes" (an explicit `readonly === false`) is now shared by the shield, this gate and the governance wrapper. Guards that disagree leave gaps exactly where they overlap.
  - **The grant is accepted only when something downstream will actually verify it.** The verifier class merely existing is the wrong question: `wrap_ability()` returns abilities untouched without SiteAgent's snapshot engine, and the loader treats `class-governance.php` itself as optional — so on a partial install a fabricated header would have passed on the strength of being non-empty. Acceptance now requires the governance wrapper to be active, not just present.
  - **The opt-out is evaluated once, before either guard touches the args.** The shield injects `meta.mcp.type = 'private'`, so a filter keyed on that meta sees a different ability afterwards and can legitimately answer differently — asked twice, a callback could decline to expose an untyped ability and then accept the plugin-injected one, closing the shield and opening the gate on the same tool. `apply_write_guards()` asks once and hands the answer to both.
  - **A dry run is exempt, as it is at execute time.** A preview-capable tool invoked with `apply` falsy writes nothing, so there is nothing for a gateway to approve; refusing it here would have taken the documented preview mode away from foreign callers, and from everyone on a site with no verifier. The preview rule is now shared with the governance layer rather than restated, for the same reason the definition of a write is.
  - **The documented exposure opt-out is honoured.** `elementor_mcp_expose_writes_to_foreign_mcp` means "I want this write reachable from other MCP servers"; gating it anyway would have left the operator with a tool that is advertised, reported as exposed, and refuses every call. The same filter with the same args decides both the shield and this gate, so a caller that opens one write tool and closes the rest gets exactly that from both.
- Fixed: **`server-info` no longer describes a fork-only site as exposed.** It reported that a metadata-ignoring server "would not be stopped a second time" whenever SiteAgent was absent — true before the transport gate existed, and the opposite of true after it. The two guards are now reported separately (`foreign_writes_refused_at_permission` alongside `governed_writes_require_grant_off_own_server`), and the note for a fork-only site says what is actually the case: foreign servers are refused outright at the permission stage, because no grant can be verified there.

## 1.30.0 — 2026-08-20

- Fixed (**security**): **write tools were reachable from any other MCP server installed on the same site** (Aura plan K7, step 1). `wp_register_ability()` publishes to a site-wide registry, not to a server — so a second MCP server on the site serves this plugin's tools without asking anyone. That is not hypothetical: Elementor's Angie 1.1.12 ships a first-party server at `/mcp/angie` whose discovery exposes **every** third-party ability whose `meta.mcp.type` is absent or `tool`, and whose `execute-ability` proxy then runs it by name (verified in Angie's `Mcp_Adapter_Ability_Discovery` / `Mcp_Adapter_Ability_Permissions`, not from its docs). On a managed site that made every mutating Elementor tool callable over a transport the Aura gateway never sees — no approval queue, no audit, no fleet visibility — which is exactly what the "every mutating agent action is queued for human approval, snapshotted, and audited" invariant exists to prevent. Two guards now close it, and they are not redundant because they cover different sites:
  - **At registration**, a write-capable ability (`annotations.readonly === false`) declares `meta.mcp.type = 'private'`. Angie's listing and its execution gate consult the same check, so a type it does not serve removes the tool from the menu *and* from the door. This is the **only** protection on a site without SiteAgent, where the governance wrapper returns every ability untouched and nothing else runs at all.
  - **At execution**, a governed write that arrived on any route other than this plugin's own MCP server must present a valid approval grant — regardless of whether grant enforcement is switched on. Enforcement is opt-in so our *own* path keeps working before the gateway mints Elementor-tool grants; that was never a reason to leave a foreign door open. The refusal happens **before** the callback runs, so nothing is written and rolled back — an unauthorized create must not insert a draft first. A valid grant still passes: a grant *is* gateway context, bound to the exact tool and params, whatever route carries it.
  - Read-only tools stay exposed to other servers deliberately — an assistant answering "what is on this page" from our data is the entire point of the read-only bridge. Only writes are withheld.
  - The new `Elementor_MCP_Call_Context` classifies the transport from `rest_pre_dispatch`, so it sees servers this plugin knows nothing about, not just Angie's. Its route is **derived from the same two constants** `register_mcp_server()` builds the route with, because a drifted copy would classify our own server as foreign and deny every governed write. WP-CLI and non-REST contexts are trusted: every co-installed MCP server dispatches over REST, and a caller with shell access does not need an ability to edit a page. It fails **closed** if the class is missing — an unclassifiable caller is the case the guard exists for.
  - Two escape hatches, both off by default: `elementor_mcp_expose_writes_to_foreign_mcp` re-exposes writes, and `elementor_mcp_trusted_write_context` trusts a named route (for an operator with a genuine second integration).
- Fixed: **the exposure report no longer names tools nothing can reach, nor warns about servers that reach nothing.** Two false-report bugs in opposite directions. First, an ability that already declares a non-`tool` `mcp.type` keeps it whatever the exposure filter says — the filter opening it writes nothing, so a foreign server still refuses to serve it — but the recorder credited the filter's answer alone and listed such an ability as exposed. Exposure is now decided by the *effective* type. Second, the "another MCP server is active" warning claimed any registered server could reach any registered ability; a stock install already carries the bundled adapter's default server, which reaches nothing here (its proxy tools require `meta.mcp.public`, which none of these abilities set), so every site got the warning. The comparison also had to be normalised: a live server's tool list is keyed by the **MCP** tool name, which the adapter derives by replacing `/` with `-` (`elementor-mcp/update-element` → `elementor-mcp-update-element`) — the same transform the grant binding already applies — so matching raw ability names against those keys would never have fired, reporting a genuinely exposed site as clean. The report now separates servers that **publish our tools in their own tool lists** — established from the registry, and warned about plainly — from other servers, which get a weaker note saying what is actually true: a server whose tools resolve targets from the site-wide registry can still reach abilities it never listed, which is why the shield is a property of our abilities rather than a list of trusted servers.
- New: `server-info` reports **write exposure** — whether writes are withheld from other servers, this plugin's own server route, and **which other MCP servers are active on the site**, read from the adapter's registry rather than probing for Angie by name (the exposure belongs to the shared registry; the next plugin to create a server inherits it). An operator auditing a managed site cannot learn this anywhere else, since the other server registers its own routes and enumerates the registry silently.
- New (tests): **the governed guarantees are now exercised over a foreign transport** (Aura plan K7, step 1b — J5's remaining gate). A valid approval grant *is* gateway context, so a properly approved call may still arrive through the second door, and everything that makes a governed write safe has to work when it does. The architecture says it does — the wrapper replaces the ability's own `execute_callback`, so snapshotting and the render check sit downstream of the transport and cannot know what carried the request — but that is an argument, not evidence, and "correct by construction" is exactly what field reports #4 and #5 kept disproving. Each governed family (page data, kit design tokens, global classes) is now driven through `wrap_ability()` → `execute_callback` with the request recorded as arriving on `/mcp/angie` and a grant presented, asserting that the v1.17 snapshot fires, a failed write rolls back, the v1.19 render check runs and reverts a page it breaks, a create-style write still snapshots the post the write site discovers, a dry-run preview needs no grant and snapshots nothing, and an expired grant denies every family before any write site is reached. A first test pins that the transport really is foreign, so the rest cannot quietly degrade into a duplicate of the own-route suite; simulating a governance layer that skips its guarantees off-route fails 13 of the 16.
- Fixed (tests): **a kit stub leaked between suites and fataled another test in some orders.** The governance suites install a minimal active-kit double answering `get_id()` and nothing else, and left it in the global; a suite whose subject calls `get_settings()` on the kit then fataled — but only when it happened to run afterwards. Latent while one class set it, visible once a second did. Both suites now clear it, and the affected test states its own precondition instead of inheriting whatever ran before it.
- Fixed (tests): the `apply_filters()` test double **dropped every argument after the first** and ignored each callback's registered `accepted_args`. A filter with a second parameter passed its tests and would have received `null` in production — the hook fires either way, so nothing failed loudly. Six assertions in the new suite depend on it. Same class of defect as the earlier no-op `add_filter` stub: a double that is easier than the real thing tests something that does not exist.

## 1.29.0 — 2026-08-20

- Fixed: **`font-family` was emitted with the wrong `$$type`, so no font set through any tool ever applied** (field report #4, part 3). `build_typography_props()` wrapped it with `Atomic_Props::string()`, but Elementor types `font-family` as `Font_Family_Prop_Type` — it extends `String_Prop_Type` and does **not** share its key. The atomic CSS engine validates every prop against the style schema and silently drops the ones that don't match, so every typography call lost its family with no error anywhere. New `Atomic_Props::font_family()` reads the key from Elementor's own prop type and falls back to `string` when the class is absent, leaving older builds as they were. Same failure class as the earlier `background-color` → `background` and `color` → Color corrections.
- Fixed: **the fallback write path never invalidated Elementor's rendered-element cache** (field report #5, part 1). Elementor caches each element's rendered HTML in `_elementor_element_cache` and clears it on every native save (`Document::save()` → `delete_cache()`); the fork's direct-meta fallback dropped `_elementor_css` and the generated CSS file but left the HTML cache alone. That fallback is exactly the path taken in non-browser contexts (CLI, REST proxy) — i.e. how the MCP writes — so a correct write served the pre-change markup until the cache TTL expired. Indistinguishable from a failed write, and intermittent, which is the combination that had agents rebuilding elements that were never broken. Both fallback sites (`save_page_data()` and `save_page_settings()`) now delete it alongside the CSS. The kit writer was already covered: it calls `files_manager->clear_cache()`, which drops the key site-wide.
- Fixed: **`add-custom-css` was a no-op on atomic elements, and variant CSS must be base64** (field report #4, parts 1.1 and 1.3). The ability wrote `settings.custom_css` unconditionally — that is the Elementor 3.x Pro control, which atomic (v4) elements never read; their CSS is compiled from `styles[].variants[]`. The write persisted, the tool reported success, and the compiled stylesheet was unchanged, so every agent that reached for this tool believed it had worked. An atomic target now gets a style variant instead: the CSS goes into the desktop/no-state variant's `custom_css.raw`, **base64-encoded**, because Elementor validates and sanitizes that field through `Utils::decode_string()` (`base64_decode( $raw, true )`) and a plain CSS string decodes to `false` and is dropped to an empty rule. The element's existing local class is reused rather than piling up new ones, its other props are preserved, and the class id is wired into `settings.classes` — a style definition nothing references compiles to nothing. Classic widgets keep the `settings.custom_css` path unchanged; the response names the mechanism used (`stored_as`).
- Fixed: **`add-nav-menu` published the wrong parameter for choosing the menu** (field report #5, part 5). The schema advertised `menu_name` as "Menu name (as registered in WP Menus)", but that is the widget's own TEXT control, rendered as the nav's `aria-label`; the SELECT that actually picks the navigation is `menu`. Convenience tools pass inputs straight through, so `menu_name: "main"` set the label and left the widget on its default menu — invisible on a one-menu site, where the default happened to be right, and the wrong navigation on every site with more than one. `menu` is now published as the selector, carrying the registered slugs as an enum when the site has menus (an empty enum would reject every value), and `menu_name` is re-described as the accessible label. A published parameter whose name doesn't match the control it claims to set is more dangerous than an omitted one — the agent has no reason to doubt it.
- Fixed: **the container tools hid capabilities the engine already had** (field report #4, part 2 — the costliest finding in either report). `build_common_props()` has always emitted correct atomic shapes for borders, radii, widths, gradients and per-side spacing, and the execute paths forward the whole input array into it — but `add-flexbox` advertised 14 parameters and none of those. Agents read the schema, concluded atomic containers could not express borders or gradients, shipped a flattened design, and wrote the "limitation" into the client's design-system document. Those apparent limits then became the primary evidence in a recommendation to build the client's site on Elementor 3.x containers instead of 4.x atomic; three of the four cited blockers were schema-discovery failures, not engine limits. `add-flexbox` and `add-div-block` now publish everything the builders accept, from a single shared source (`Atomic_Styles::style_props_schema()`) so the schema cannot drift from the builder again — the flex params are excluded for `add-div-block`, which is not a flex container. Tests pin the two together in both directions: every published parameter must actually produce a prop, and an advertised no-op fails the build.
- New: **`position` and `box-shadow` on atomic elements** (field report #4, part 2 — the two capabilities that were genuinely missing rather than merely unpublished). `build_common_props()` had no mapping for either, so absolutely-positioned compositions could not be expressed at all: the design's four badges orbiting a checkout card shipped as a row above it and were ultimately replaced by a Lottie to recover the arrangement, and all seven of the design's shadows were dropped. Both now emit the shapes Elementor's style schema declares — `position` as its String enum with Size offsets under the logical `inset-*` names plus a Number `z-index`, and `box-shadow` as an array of `shadow` objects whose members are all required, so setting any one shadow param produces a complete shadow using Elementor's own defaults. **The input key is `css_position`, not `position`:** the layout tools already publish `position` as the insert index, and reusing the name would forward an integer into a string enum. The offsets are published under **logical** names (`offset_block_start`, `offset_inline_end`, `offset_block_end`, `offset_inline_start`) because that is what Elementor's schema declares and the inline axis follows text direction — calling them `offset_left`/`offset_right` would have named the wrong edge on every RTL page while looking correct in LTR review. The atomic **widget** tools (headings, buttons, images) now derive their style schema from the same shared source as the containers, so positioning and shadows are discoverable there too rather than working but unadvertised.
- Fixed: **`update-atomic-widget` could not change a style at all** (field report #4, part 1.2). The tool wrote only `settings`, but on an atomic element size, spacing and appearance are not settings — they live in the `styles` map. A padding or width sent through `settings` merged, saved, reported success and was dropped by Elementor's parser. Three separate agents on that build independently verified against the compiled CSS and each concluded that **delete-and-recreate was the only reliable path** for a styling change, which meant correcting one card's padding required rebuilding the card and everything inside it. The tool now accepts the same flat style params as the add-* tools (including typography) and merges them into the element's base style variant, preserving props it wasn't asked to change and wiring the class into `settings.classes`. `settings` remains for content. An update that provides neither is now refused with `nothing_to_update` instead of reporting success. Composite properties are merged member-wise rather than replaced: on Elementor 4 the four padding sides collapse into a single `padding` prop holding a `dimensions` shape, so a shallow merge would have dropped three sides when the caller touched one — the same partial-update data loss, one level down. Lists (a box-shadow array, a gradient's colour stops) are still replaced wholesale, since a new list is a new value rather than an edit.
- New: **`server-info` — an always-available diagnostic that cannot be disabled** (field report #5, part 2a). A fresh install once presented as "the MCP server exposes zero tools" with nothing anywhere to explain it: no server-info response, no log line, nothing saying how many abilities were registered versus suppressed. The only recourse was reading the plugin source to discover that the controlling option existed. The same blindness recurs after upgrades, when the defaults seeder re-disables the Pro-badged set and tools vanish from a working install — it took an ability-vs-tool diff to notice 36 missing. The new tool reports plugin / Elementor / Elementor Pro versions, whether atomic is active, the MCP adapter's resolved source and version (bundled vs standalone — they answer the same client differently), whether the server endpoint is switched on, and **registered vs exposed vs suppressed** ability counts with the suppressed slugs, the option key responsible, low-tools-mode state and the seeder's version counter — plus plain-language notes explaining any gap. It is exempt from the disabled-tools option and from low-tools mode: a diagnostic the thing it diagnoses can switch off is no diagnostic at all. `exposed` reports **0** when the Connection toggle is off, since nothing is exposed then regardless of what survived the filter — a separate `would_expose` says what comes back when it is switched on. Withheld abilities are attributed by cause — `plugin_settings` versus `other_filters` — because `elementor_mcp_ability_names` is a documented public hook and another plugin's removal would otherwise be blamed on the local option, sending an operator hunting slugs that are not in it. The exemption is enforced after the **whole** filter chain, not just this plugin's callback, so another plugin's curated allowlist cannot silence the diagnostic; and abilities *added* through the same hook count as registered, so the exposed count can never exceed the registered one. The diagnostic is instantiated behind a `class_exists()` guard, because the loader treats every source file as optional and registering this one first meant an unguarded failure would have cost every tool that registers after it. Accounting covers the whole hook: an ability another plugin adds before this one's filter and this one's settings then remove is still reported as withheld rather than vanishing from the counts, non-string values a callback returns are discarded rather than allowed to abort registration, duplicate appends are counted once, and names that resolve to no ability are excluded from the report — the MCP adapter skips those too, so counting them would overstate it. That resolution happens when the report is generated, never at registration: registration runs during `wp_abilities_api_init`, where another plugin's ability may not have registered yet, so checking there would discard a legitimate name.
- Fixed: **the global and system-kit colour/typography tools now point at each other** (field report #5, parts 2b and 3). `replace-system-colors` was available and unused for an entire build that spent rounds fighting the global palette: it reads as a destructive bulk operation rather than "set the brand palette", while the obvious-looking `update-global-colors` appends to `custom_colors` and never touches the four system slots that every widget's Global Color picker references — so the brand palette lands and Elementor's stock `#6EC1E4` stays bound to the roles that matter. Both descriptions now say what they write, and each names the other. No new ability: report #4 proposed one, and report #3 corrected that — it already existed, and the gap was discovery.

## 1.28.0 — 2026-08-19

- New: **GitHub self-updater.** The plugin now offers its own updates on the normal WordPress Plugins / Dashboard → Updates screens, pulled from this repository's tagged GitHub Releases (bundled Plugin Update Checker 5.6, wired in `includes/class-updater.php`; ported from the Digitizer Pro Tools updater). Detection is release-ONLY — a pushed version tag without a published Release never offers an update — and every request to GitHub (the check *and* the package download, across the release-asset redirect hosts) carries a neutral `elementor-mcp/<version>` user agent instead of WordPress's default, which would hand the site URL to GitHub. When a Release attaches a built `elementor-mcp*.zip` asset it is preferred; otherwise the tag's source archive is served. To ship an update: bump the plugin version, tag `v<version>`, publish the Release.

## 1.27.1 — 2026-08-08

- Fixed: **the Angie bridge never loaded in the Elementor editor** — the one surface it exists for. Its bundle was registered on `admin_enqueue_scripts`, which the editor never fires: that screen is rendered from `admin_action_elementor`, before admin-header.php, and Elementor then calls `remove_all_actions( 'wp_enqueue_scripts' )` and rebuilds a front-end style document from its own hooks. The bridge now also rides `elementor/editor/after_enqueue_scripts`, the hook Angie's own editor integration uses, and guards against a double localize.
- Fixed: the bridge registered through `registerServer()` with a config carrying no `type`. The SDK answers that with a warning and hands off to `registerLocalServer()` **without awaiting**, so the promise resolved before the registration had begun and a failure inside it could never surface. It now calls `registerLocalServer()` directly.
- New: `window.emcpAngieBridgeDebug` — `isAngieReady()`, `registrations()`, `pending()`. A registration that stays queued is otherwise indistinguishable from a successful one: nothing throws, nothing logs, the tools simply never appear. It exposes state, not authority; every tool call still goes through the REST routes, the server-side allowlist, the read-only invariant, and each ability's own permission callback.

Verified live on WP 6.9 / Elementor 4.2.2 / Angie 1.1.11: Angie discovers the six read-only tools and executes them (`list-pages`, `list-global-classes`, `list-variables` all returning 200).

**The bridge's tool list is independent of the admin Tools toggles.** `register_groups()` registers every ability with the Abilities API; the `elementor_mcp_ability_names` filter only trims the name list handed to the MCP Adapter server. The bridge resolves its own six-entry allowlist through `wp_get_ability()`, so switching tools off on the Tools tab — including low-tools mode — does not empty it.

## 1.27.0 — 2026-08-07

- New: **Four upstream correctness ports (P3.3 round 1).**
  - **Silent-save verification.** `Document::save()` can return truthy in 4.x / atomic / REST contexts while persisting nothing; `save_page_data()` now re-reads `_elementor_data` after a truthy native save and takes the direct-meta fallback instead of reporting a phantom success.
  - **Local style classes are re-minted on duplicate.** Duplicated v4 elements shared the source's `e-<id>-<hash>` classes, so editing one bled style into the other.
  - **Fatal-proof ability registration.** A group that throws no longer takes wp-admin down site-wide; whatever registered before the failure survives.
  - **`structuredContent` normalization.** Lists/scalars/null returned by an ability are wrapped under `data` at the registration seam, so strict MCP clients never reject a top-level JSON list.
- New: **Whole-tree atomic prop coercion (P3.3).** Settings written through any tool are now coerced against the widget's own prop schema before the save, so a plain value handed to an atomic prop (`title: "Hi"`) is stored as the typed envelope Elementor expects instead of silently rendering as nothing. `Elementor_MCP_Atomic_Props::coerce_tree()` runs at the top of `save_page_data()` — before the governance snapshot — and walks every element, deriving the schema from `widgetType` for widgets and `elType` for atomic containers.
  - **Candidate envelopes come only from members the prop declared itself.** Each prop type is asked what it accepts (`get_key()`, `get_prop_types()`, `get_shape()`, `get_item_type()`, `get_meta_item('aliases')`) and a candidate is built per declared member; the generic primitive fallback runs **only** for props that did not describe themselves. This is the rule the review rounds converged on: Elementor's primitive validation accepts an "empty" enveloped value for a non-required prop *before* the type/enum check, so guessing a foreign envelope stores a malformed prop that validates and then renders nothing.
  - Prop aliases are applied, so a param under an old name still lands on the current prop.
  - Shapes unwrap their own outer envelope before scanning; typed arrays coerce their items through `get_item_type()` and are rebuilt.
- New: **Atomic style wiring.** `update-element-settings` now hoists root-level `styles` / `editor_settings` out of a settings payload into their proper top-level keys, deep-merges rather than replaces, and syncs local class references so a style that was written is actually referenced from `settings.classes` (it renders nothing otherwise).
  - Hoisting is gated on a **positive** atomic signal — root atomic keys, a typed prop in settings, or a registered `get_props_schema()`. The `e-` slug prefix is a convention, not an authority, and a classic widget carrying such a slug must not be hoisted. When there is no answer, the element is treated as classic: an un-hoisted key is inert, a wrongly hoisted one destroys data.
- New: **Shared atomic convenience-param mapper** (`Elementor_MCP_Atomic_Widget_Map`) — the single source of the friendly-param → typed-prop mapping for the eight atomic types, consumed by both the `add-atomic-*` tools and `build-page`, so the two produce byte-identical settings for the same input. Previously `build-page` passed settings through raw and an atomic widget given friendly params came out empty.
  - `build-page` also passes **already-typed** props through untouched: the mapping sanitizes its inputs and `sanitize_text_field()` on an array returns `''`, so a caller that typed a prop itself had exactly that value erased. Typed props are excluded from the mapping and from the flat style params, and overlaid on the mapped result.
- Fixed (**security**): the attachment alt write (`_wp_attachment_image_alt`) implied by `add-atomic-image` / `build-page` is now **authorized against the attachment** (`current_user_can('edit_post', $attachment_id)`) and **deferred until the page save succeeds**. Editing the page a media item is placed on does not grant edit rights over the media item itself, and a failed save must not leave a stray alt change behind. A media prop the caller typed itself **cancels** the write outright: the alt belongs to the image the widget actually renders, and the friendly `image_id` then names an attachment that is not on the page.
- Fixed: **upstream-correct media shapes.** `e-image` emits an id-XOR-url `image-src` with the attachment id as an `image-attachment-id` envelope and the alt inside `src`; `e-self-hosted-video`'s `source` is the `video-src` shape (id XOR url) on 4.x, where a bare url envelope makes Elementor refuse the element outright.
- Fixed: the SEO content extractor descends through an atomic image's `src`. For a **media-library** image the library's own alt is authoritative — Elementor renders `_wp_attachment_image_alt` and ignores `src.alt`, so an empty library alt is the real state and must be reported as such. A url image still uses the payload alt; classic widgets are untouched.

## 1.26.0 — 2026-08-04

- New: **Angie bridge (read-only v1).** An opt-in, **off-by-default** integration that registers "**Aura Design Engine**" as an MCP server inside Elementor's Angie assistant via the public `@elementor/angie-sdk`. Exposes exactly **six read-only inspection tools** — `list-widgets`, `get-widget-schema`, `get-page-structure`, `list-pages`, `list-global-classes`, `list-variables` — so Angie can answer "what's on this page / which widgets, classes, variables exist / what settings does X take" through the fork's abilities. **No write tools are exposed**: Angie is an agent (the LLM chooses the exact tool + params), and this cookie/capability transport cannot carry the per-mutation human approval the governed write path requires — a mutating ability reached through the bridge returns `bridge_writes_phase_b`. Governed writes remain exclusive to the MCP connection; a Phase B (writes queued through the Aura approval flow) is spec'd separately in the Aura plans repo.
  - Server side (`includes/class-angie-bridge.php`): REST namespace `emcp/angie/v1` (`GET /tools`, `POST /execute/{tool}`), cookie session + `X-WP-Nonce`, `edit_posts` gate on the routes plus **each ability's own permission callback via `WP_Ability::execute()`** on every call. The allowlist is enforced **server-side with a read-only invariant**: an ability must carry `annotations.readonly === true` and not `destructive` to list or execute — a filtered-in or drifted mutating ability is rejected at runtime, and anything outside the allowlist is a plain 404 (the bridge does not advertise the rest of the registry). Experiment-gated abilities (global classes / variables on non-v4 sites) drop out of `/tools` naturally. Responses are MCP `CallToolResult`-shaped and tagged `_meta.source: angie-bridge` for attribution.
  - Browser side (`assets/angie-bridge/`, clean-room from the SDK's public API): a small bundle that registers the server with Angie (`AngieMcpSdk` → `waitForReady()` → `registerServer`), forwarding `tools/list` and `tools/call` to the REST routes over `wp.apiFetch`. ## 1.25.0 — 2026-07-08

- New: **Global-classes governance** (winning-plan P2, plank 2) — the Class Manager writers (`create` / `update` / `delete-global-class`) now get snapshot-before-write + rollback, closing the last design-token reversal gap. In Elementor 4.x a global class is **not** kit meta but its own CPT post (`e_global_class`), indexed by kit meta, and a **delete cascades**: it removes the class post AND rewrites every page whose `_elementor_data` referenced the class. Reversing that is a multi-post transaction, so a meta-only snapshot could not do it.
  - Each of the three writers declares `meta.governance.scope = 'global-classes'`. At the repository write site (`apply_change`), a lazy `Governance::before_global_classes_write()` captures the **active kit + the touched class CPT posts + the pages a delete cascades to** in ONE `snapshot_posts()` call (SiteAgent's plank-2a multi-post primitive), so a single restore rolls the whole transaction back on failure. The affected pages are resolved the same way, and at the same point, Elementor itself does (`Global_Classes_Relations`). Lazy-at-write-site means a tool rejected during input validation never snapshots — no false rollback of a concurrent change.
  - **Fail-closed:** refused (`governance_snapshot_failed`) when there's no active kit or the affected pages can't be resolved; refused (`governance_snapshot_unavailable`) when the installed SiteAgent lacks `snapshot_posts` (a meta-only rollback would half-restore the kit's id-map to a deleted class post). Grants (opt-in) are checked first; no render check (site-wide, not one page).
  - `apply-global-class` is unchanged — it writes **page** `_elementor_data`, already covered by the page write-site governance since v1.17.
  - The snapshot also captures the design-system sync-to-v3 kit map (`_elementor_global_classes_sync_to_v3`, mutated by apply_changes on the non-preview path) and each class post's **reverse usage index** (`_elementor_global_class_using_documents`, which a delete's `$post->delete()` drops and `get_posts_by_style()` reads first) plus the pages' usage-indexed flag, so a rollback keeps a later cascade lookup correct. The pages' multi-valued `_elementor_used_global_class` is deliberately not snapshotted (SiteAgent's `snapshot_posts` round-trips only single-valued meta — capturing it would clobber a page's other classes); it self-heals on the page's next save and the restored reverse index covers lookups meanwhile. **Fail-closed corollary:** when a deleted class is in use but its reverse index is *empty* (the affected pages were found only via that un-restorable multi-valued fallback — e.g. imported / un-reindexed pages), the governed delete is **refused** (`governance_snapshot_failed`, "usage index is not yet built") rather than done half-reversibly; re-save the pages (or let Elementor rebuild its index) and retry.
  - Known limit: a create that fails *mid-write* can leave one orphaned (unreferenced, inert) class CPT post — its post id isn't known at snapshot time; the kit id-map reverts so Elementor never surfaces it.

## 1.19.0 — 2026-07-07

- New: **Post-write render check** for governed page writes — the third and final plank of P0.2. When enabled, after a successful governed write the edited page's front end is fetched and, if it comes back **definitively broken**, the write is reverted to its pre-write snapshot and the tool returns `governance_render_failed` (or `governance_rollback_failed` if the revert itself could not complete). This closes the loop: a write that succeeds at the data layer but produces a white screen / fatal page no longer ships.
  - **Definitely broken =** HTTP 5xx (a real PHP fatal is served by WordPress's fatal handler with a 500 status) or an empty body (WSOD). A 200 body is never scanned for a fatal string, so ordinary page copy can't trip it.
  - **Fail-safe.** A transient loopback failure (timeout, DNS, connection reset — anything returning a `WP_Error`), a page that isn't a published, publicly-viewable page (drafts, and Elementor `elementor_library` templates/popups are skipped), or a page whose **pre-write render could not be confirmed healthy** (already broken from maintenance mode / an unrelated 5xx, or an inconclusive baseline probe — the page is baselined before the write) is treated as **inconclusive and never reverts a good write**. A rollback happens only when a confirmed-healthy page turns broken — a breakage the write actually introduced. The probe is cache-busted so a warm page cache can't mask a fresh fatal, does **not follow redirects** (an off-origin redirect would be an SSRF vector — a redirecting page is treated as inconclusive), and bounds the buffered body so a large page can't exhaust memory.
  - **Edits only.** The check runs for edits to an existing page (the write carries a `post_id`); create-style tools are not render-checked, since reverting a create would restore absent meta yet leave the newly inserted post behind.
  - **Opt-in** (default OFF): the check adds a loopback request per governed write, so operators enable it explicitly via the `elementor_mcp_render_check` option / filter (or `emcp_governance_render_check()`). Fires `elementor_mcp_governance_render_reverted` when it reverts. The opt-in is cleared on uninstall.
